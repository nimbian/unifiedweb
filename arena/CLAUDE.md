# CLAUDE.md — D&D Arena (Twitch Chat Battle Game)

## What this project is
A Twitch community stream game: viewers create persistent D&D characters via chat commands and enter them into recurring 60-second damage-race arena rounds rendered in a Godot 2D overlay. Python game server is authoritative; Godot is a dumb renderer; PostgreSQL is the store.

## Stack (locked — do not substitute)
- Python 3.12+, `twitchio` (chat + EventSub later), `asyncpg`, FastAPI (hosts the Godot-facing WebSocket only — it is NOT the chat ingress), asyncio round loop. Single process.
- PostgreSQL 15+. Godot 4.x / GDScript for the client.
- Config (timings, XP tables, class coefficients, asset lists) lives in a hot-reloadable TOML file, never hardcoded.

## Hard rules (never violate)
1. **All randomness is server-side.** Stat rolls, d20s, sprite/dummy/background selection. Godot receives outcomes only and holds no persistent state or game logic.
2. **Only the server writes to Postgres.**
3. **Chat ingress only through platform adapters.** Adapters normalize messages to `{platform, platform_user_id, display_name, text, timestamp}`; no twitchio (or other platform-library) types past the adapter boundary. Adapters are isolated tasks — one crashing must not affect the round loop. Twitch is the only v1 adapter; YouTube/TikTok come later (PLAN.md §6.5).
4. **Users are keyed on `(platform, platform_user_id)`**, not a twitch_id column. Same human on two platforms = two users. No account linking.
5. **The overlay event ticker is the primary feedback channel.** Every command outcome must emit a `ticker` WebSocket message. Twitch chat replies (≤ 1 line) are a mirror, never a dependency — later platforms can't receive bot messages.
6. **Wizard's primary stat is WIS.** This is intentional per the design owner — do not "fix" it to INT.
7. Damage formula: `class_coeff × ((PS × d20_mult) + SS)`, **accumulated as floats, rounded only at display/persistence**, with a global ×10 display scale from config. Nat 1 = miss (0 dmg). Nat 20 = crit: `class_coeff × ((PS × 2.0) + SS) × 2`. The 18-entry multiplier table covers rolls 2–19 only (see PLAN.md §4.4).
8. Character names ≤ 20 chars, alphanumeric+spaces, profanity-filtered (reject, don't sanitize).
9. Twitch EventSub handlers (Phase 2) must be idempotent via the `processed_events` table.
10. Voided/crashed rounds must not consume a character's 25-battle lifespan.
11. **Do not equalize Hall-of-Fame odds across classes.** Swingy classes (Wizard) owning single-hit/single-round records while steady classes (Monk) accumulate wins is intentional design, not a bug.

## Balance gate
After any change to rules, classes, coefficients, races, or abilities: run the simulator at **100k rounds** (10k is too noisy — ±0.3pp standard error) with level-matched characters. **Tune coefficients against win rate, not mean DPS**, using the damped tuner `coeff_new = coeff × (fair_share / win_rate) ** damping`. Every class must land in its band = **fair win share ± a per-engine half-width**, where fair share = `100/fighters_per_round` (**12.5% at R2's 8 slots**, was 10% at 10). Bands are computed by `sim.band_for(engine, cfg)` so they re-center automatically with the slot count. At 8 slots both engines use **±0.7 → 11.8–13.2** (`CLASSIC_BAND_HALF` was widened 0.5→0.7 at the 8-slot regime — the classic max-of-8 spread is ~0.9pp, same irreducible-variance reason moore is ±0.7; **flagged in sim.py for owner review**). Report the table in your summary.
- Now that races + abilities exist, the **authoritative gate is the WITH-races table** (`python -m server.sim --rounds 100000 --races` — every real character has a race). Tune with `--tune --tune-races --write`. The raceless table is only the reference baseline for per-race DPS impact (target ≤ ~5% vs neutral). With arena events live (`event_chance > 0`), also check `--events`: the races+events **mixed** table must stay in band (forced single-event tables are worst-case stress, directional only). Notes/deviations: independent luck is authoritative (CRN biases this max-of-10 metric and skips abilities); the damped exponent is under-relaxed from 0.5 to `TUNE_DAMPING` for stable convergence; Human/Orc passives were trimmed below their literal spec values (Human `damage_mult = 0.985`, Orc first-hit 2.0→1.9) to meet the ≤ ~5% target — owner-approved, do not "restore" them.
- **R2 round shape is live: 90s / 8 slots** (fair share 12.5%). Both engines re-tuned at 90s/8; WITH-races gates pass every seed within **11.8–13.2** (classic 11.96–13.00, moore 11.94–13.11 across seeds 1337/1/2/3), per-race impact ≤4.8%. `TARGET_WIN_RATE` retired; the tuner targets `fair_win_share(cfg)` and renorm makes it scale-invariant.
- This gate + tuner get rebuilt around hit-chance/AC/attack-speed at R1 (PLAN.md §13.2); the classic path above still governs live play until the moore engine flip.
- **Moore engine gate (R1, `--engine moore`)**: band is **fair share ± 0.7pp** (`MOORE_BAND_HALF`; **11.8–13.2 at 8 slots**). The moore model has an irreducible ~0.8pp win-rate spread (flat-variance smoothing ∝√N vs crit-lumpiness ∝1/√N across the 3.3× cadence range — docs/R1_combat_math.md §8), so the strict ±0.5 band is unreachable by tuning; owner-ratified the wider band since MooreDnD centers on monster battles + performance gold, not damage-race win parity. `damage_variance = 150` (deviation from the doc's 75; the doc value leaves a 3.2pp spread). moore coeffs live in `moore_coeff` (separate from classic `coeff`), tuned with `--tune --engine moore --tune-races`. Races + abilities are re-expressed in moore math; the authoritative gate is the **WITH-races** moore table (`--engine moore --races`). The neutral-race table is expectedly off (fighter low, paladin high — ability variance heterogeneity the coeff can't equalize without the race mix); it is the reference, not the gate. The moore tuner is engine-aware: `MOORE_TUNE_DAMPING = 0.05` (not classic's 0.15) — moore's win-rate elasticity is ~2pp per 1% coeff, so 0.15 diverges/oscillates (`tune_damping_for(engine)`). Fixed `write_coeffs_to_toml` so re-tuning never duplicates an existing `moore_coeff` line.
